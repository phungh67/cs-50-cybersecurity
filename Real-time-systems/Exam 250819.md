b. Why does the worst-case execution-time analysis of a piece of code should be as tight as possible.

a. Baseline case (in which $y=0$)
The $WCET_{baseline}$ will be:
- Declare costs 1
- Comparison costs 2
- Assign costs 1
- Return costs 2
So the $WCET_{baseline}=6$

In the branch which y is not zero:
- Declare costs 1

	- Assign costs 1

	- Subtract costs 3

- Multiply costs 5

In total $WCET_{branch}=28 + WCET(y-1)$

Summary:
$$
WCET = WCET_{baseline} + WCET_{branch} = 6 + y.28 = 0.x + 28.y + 6
$$
b.
A tight `WCET` bound reduces pessimism in schedulability analysis and prevents hardware over-provisioning. If a `WCET` estimate is too loose (massively overestimated), the total system utilization ($U$) or processor demand ($h(L)$) will artificially inflate. This will cause scheduling tests to falsely report the system as unschedulable, forcing engineers to buy faster, more expensive processors or remove features unnecessarily to fix a "problem" that doesn't actually exist in reality.

Long-short: tight reduces the pessimism in the analysis for prevents the hardware over-provisioning[^1]

c. Describe the meaning of priority inversion in the context of single-processor scheduling. Explain the concept of priority inheritance protocol (PIP) as used in access-control protocols for critical regions. Would it be correct to say that the PIP is a deadlock-free protocol? Motivate your answer?

- Priority inversion occurs when a high-priority task is blocked from executing because it is waiting for a shared resource (like a mutex) that is currently held by a lower-priority task.
- The Priority Inheritance Protocol (PIP) solves unbounded priority inversion by temporarily elevating the priority of the lower-priority task holding the resource to match the priority of the highest-priority task waiting for it. Once the resource is released, the task drops back to its original priority.
- **Is PIP deadlock-free?** **No.** PIP is completely vulnerable to deadlocks if tasks lock multiple mutexes in different orders, creating a circular wait (e.g., `T1`​ holds `S1`​ and waits for `S2`​, while `T2`​ holds `S2`​ and waits for `S1`​).

d. Consider a task set with independent periodic tasks, for which it applies that the deadline of each task is equal to its period. Assume that the task set is known to be not schedulable on a single-processor system using static task priorities. Would a necessary feasibility test report the answer ’True’ or ’False’ when applied to that task set? Motivate your answer! 

- **Answer:** It could report **either 'True' or 'False'**.
- **Motivation:** By definition, a necessary test checks the bare minimum conditions required for schedulability (e.g., total utilization $U≤1$). Just because a task set is known to be _not_ schedulable does not mean it failed the necessary test; it might have passed the necessary test (reporting 'True') but failed due to other factors like worst-case blocking times or interference. It could also report 'False' if it is severely overloaded. Therefore, you cannot definitively say it will report one or the other without looking at the exact task parameters.

e. The `TinyTimber` run-time scheduler supports the concept of concurrent programming. Describe how the application programmer instructs the `TinyTimber` kernel to create a concurrent execution of a given piece of program code.

- **Answer:** The application programmer creates concurrent execution by using the **`ASYNC()`** macro.  
- **Context:** `ASYNC(object, method, argument)` instructs the `TinyTimber` kernel to place the method invocation into the ready queue to be executed concurrently as an independent thread/task, rather than executing it sequentially like a standard C function call.

De-scribe how the application programmer instructs the `TinyTimber` kernel to read the current value of the system clock. Also state the resolution (that is, the length of a time unit) of the `TinyTimber` system clock in the laboratory system used in the course. 

- **How to read the clock:** The programmer instructs the kernel to read the current system clock value by calling the **`CURRENT_OFFSET()`** macro.

a. Consider a synchronuous (all offsets $O_i$ are identical) task set for which it applies that the deadline of each task does not exceed its period (that is, constrained-deadline tasks with $D_i \le T_i$). Assume that the task set is known to be not schedulable on a single-processor system using preemptive scheduling and static task priorities. If one of the tasks in the task set would increase its offset by one time unit, keeping its other task parameters intact, would the task set still be unschedulable on the single-processor system. Motivate the answer?

The task set will not necessarily still be unschedulable. Motivation is from the Liu & Layland's Critical Instant Theorem. Since a synchronuous arrival, where all the offsets $O_i$ are the same, tasks produce the max interference to each others. If a taskset cannot survise with this case means it can not survise the worst case scenarion, hence, unschedulable.

But increasing one time unit for any task's offset, means that task is shifted a little, thus reducing the demand for processor right at that point. Which can result in a schedulable set (probability, not the guarantee).

b. Explain the outcome result of these feasibility test:
- Liu & Layland's feasibility test.
- Response Time Analysis test for DM.
- Response Time Analysis test for RM.

First, LL feasibility test's outcome is unknow. Since it is only a sufficient test, so a "True" outcome means schedulable, but a "False" outcome does not have the same meaning. Further inspections are needed to be done to determine the schedulability of a tasks set. Also, the LL assumes that $D_i=T_i$, so with some sets in which $D_i \le T_i$, it will produce pestimisstic result - a false negative.

Second,  RTA is an exact test (both necessary and sufficient), meaning it perfectly reflects reality. Second, Deadline Monotonic (DM) is proven to be the optimal static priority-assignment policy for constrained-deadline systems ($D_i \le T_i$). If the system is already known to be schedulable under RM, it is mathematically guaranteed to be schedulable under the optimal DM policy. Therefore, the exact test will confidently report 'True'.

Finally, RTA is an exact test. Because the problem explicitly states as a fact that the system is schedulable under RM, the exact mathematical calculation of the worst-case response times will perfectly reflect this reality ($R_i \le D_i$ for all tasks). Therefore, it must report 'True'.
